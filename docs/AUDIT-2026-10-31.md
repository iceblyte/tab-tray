## 0. 结论

**只完成了 v1，不是「插件全部开发完成」。**

- v1 的功能闭环基本完成：PRD v1.4 的 F1–F9 能力都能在代码里找到落点，A1–A10 / M1–M10 的人工验收清单全部勾选，1.0.0–1.0.2 已发布，社区市场上架。
- 但 v1 本身还有 6 个收尾项：1 个数据安全边缘缺陷、1 个发布工程缺口、4 个用户可见或文档问题；PRD §2.3 的 v1.1/v2 路线图基本未开始，其中 2 项已经被 R6 修订**逻辑上作废**。
- 当前不是「继续加功能」的最佳时点：插件上线 2 天、0 issue，需求验证（PRD V5）还没有输入。建议先做 4 周反馈门 + v1.1 加固，再决定 v2 主线。

### 0.1 两个完成度

| 维度 | 估计 | 说明 |
|---|---|---|
| v1 交付完成度 | **约 95%** | 功能闭环；剩 6 个收尾项，未发现阻断性缺陷 |
| 产品路线图完成度 | **约 40%** | v1.1/v2 的回收站、多选、智能分组等未开始；2 项已作废 |

### 0.2 三个最重要的判断

1. **工程质量高于同类**：core/UI 分离、123 条单测、原子写 + `.bak` + 冲突仲裁、发布 attestation，这些是真实优势，应继续守住。
2. **最大的风险不是功能少，而是「信任」和「发现」**：手动分组需要用户先付出设置成本；没有 undo/回收站，替换式展开会让新用户不敢用；没有 CI，一次坏提交就可能进 Release。
3. **v2 不要做垂直标签页**：Vertical Tabs 已有 87k 下载且仍在活跃发版，正面竞争是以小博大；PRD 的「原生标签栏内」定位是对的，v2 应沿这条线做「自动分组」，而不是换形态。

## 3. 代码走查发现

> 严重度定义：P0 = 数据丢失 / 发布完整性；P1 = 用户可见缺陷或维护成本；P2 = 体验 / 增长。

### 3.1 P0

**P0-1 没有 CI，Release 只跑 build**

- `.github/workflows/` 只有 `release.yml`；它执行 `npm ci` + `npm run build`，**不跑 lint / typecheck / test**。
- 后果：一个测试红、类型错的提交，只要 build 能过，就能被打 tag 并发布；对「持久化是产品理由」的项目，这是发布完整性问题。
- 建议：新增 `ci.yml`（push/PR：lint + typecheck + test + build），Release 复用同一套 check（`workflow_call` 或 `needs`）。

**P0-2 损坏文件保留失败时仍会覆盖主文件**

- `core/persist.ts:293-303`：主文件不可解析 → 尝试 `rename` 为 `data.json.corrupt-*`；**rename 抛错时只记日志，然后把 `#mainHealthy` 设为 true，继续 `process(mainPath, …)` 覆盖原文件**。
- 这正是 F5 最该守住的场景：用户手改坏了 `data.json`，插件本应留存原字节，结果在 rename 失败（权限 / 锁 / 适配器差异）时把它覆盖掉。
- 建议：rename 失败 → 抛错 / 保持 `#mainHealthy=false`，本次写入中止并走重试；新增「rename 失败」单测（fake port 注入故障）。

### 3.2 P1

**P1-1 Windows 库外条目的显示名**

- `ui/file-utils.ts:3` 的 `baseName()` 只按 `/` 切；`tests/paths.test.ts:22` 明确 `file:C:\notes\note.md` 是合法形态。
- `Sidebar.svelte:598` 用 `baseName(entry.path)` 显示库外条目 → Windows 上会显示整条 `file:C:\...\note.md`，而不是 `note.md`。
- 影响：库外节可读性；不影响入组（库外本来就不入组）。
- 建议：新增 `displayName(path)`（剥离 `file:`、同时按 `/` 和 `\` 切），单测覆盖 POSIX / Windows / UNC。

**P1-2 文案与 R6 矛盾**

- `i18n/en.ts:29` / `zh-cn.ts:26` 的 `member.pinnedHint` 仍写「挂起成员…取消固定后自动恢复」；R6 已改为「固定即移出，取消固定不回组」。
- `notice.collapsedPinned`（`en.ts:83` / `zh-cn.ts:74`）在稳态下不可达（组内不会有固定成员），但代码仍保留分支（`controller.ts:312`）。
- 建议：改写 `pinnedHint` 为「已固定——固定会移出分组」；`collapsedPinned` 保留为竞态兜底并注明，或删除。
- 另：`settings.about.title`、`notice.closeFailed` 未被引用（死键）。

**P1-3 文档漂移**

- `ACCEPTANCE.md`：基线 `dbae042`、90/90、131 KB → 当前 `c45dcde`、123、141,499 B。
- `DESIGN.md`：§1.4 写 IIFE（实际 CJS）；§2.4 写 Vitest 4（实际 5.0.5）；§2.5 写 Biome 2.5（实际 2.6.3）；§3.1 / §3.7 仍有 `ui/tab-manager/`；§3.3.10 仍描述独立右侧面板；§4.3 写 `ci.yml`（不存在）且上传 `styles.json`（应为 `styles.css`）。
- `PRD.md`：§1.4 / §2.3 与「染色进 v1」「F9 合并」「R6 固定即移出」不一致；§2.3 两项候选已作废。
- `prototype/`：`09-tab-manager.html` 仍是右侧面板 + 第二 ribbon；README 却说「prototypes the implementation follows」。
- 建议：新增 `docs/AS-BUILT.md` 或在 PRD/DESIGN 顶部加「as-built 2026-10-31」修订块；不要重写历史决策，保留可追溯性。

**P1-4 紧凑固定行的运行时自检缺失**

- `workspace/compat.ts` 只做静态探测（`.workspace-tab-header-inner` / `-title`）；`ui/pinned-row.ts:68` 用 `.workspace-tab-header-status-icon.mod-pinned` 判固定。
- 如果 Obsidian 改了固定指示器的类名，静态探测仍会通过，但紧凑行会**静默不生效**，设置开关仍是可用状态——违反 F4/D18 的「运行时自检级：映射失败 → 降级 + Notice」。
- 建议：首次 pin 事件时，用 `leaf.getViewState().pinned === true` 的 leaf 找到 `leaf.tabHeaderEl`，检查其内部是否有固定指示器；不匹配 → `compactPinnedRowAvailable=false` + Notice（一次性）。

**P1-5 没有 undo / 回收站**

- 替换式展开会关闭当前窗格的非固定标签；收起会关闭组员。代码里没有关闭栈，用户误点只能靠 Obsidian 自己的「重新打开」或手动找文件。
- PRD §5.1 R5 明确把「撤销关闭标签兜底」列为缓解；未实现。
- 建议：v1.1 做**内存级**关闭栈（最近 20 条，`{path, windowId, reason, closedAt}`）+ 命令「重新打开关闭的标签」；不做持久化，避免第二套事实源。

**P1-6 没有诊断出口**

- 没有 telemetry 是优点，但用户报「标签不收缩 / 染色不生效」时，维护者拿不到版本、DOM 探测结果、tab 数、`data.json` 路径。
- 建议：v1.1 加「复制调试信息」命令（版本、平台、组数/成员数/打开标签数、probe 状态、compact/groupColors 设置、`data.json` 路径、最近 30 条 `[tab-tray]` 日志）。用户主动复制，不自动上传。

**P1-7 Popout 中的 `svelte:document`**

- `Sidebar.svelte:573` 用 `<svelte:document onclick=… onkeydown=…>`；Svelte 编译到全局 `document`。侧栏被拖入 Popout 后，Popout 的点击 / Escape 不会触发，菜单 / 色板不会点外关闭。
- 需在真实 Obsidian 验证；若成立，改为在 `$effect` 里对 `contentEl.ownerDocument` 注册 / 清理。
- 同类：`menus.ts:63-72` 的 contextmenu 只在 `window-open` 时给新窗口注册；启动时已存在的 Popout 可能漏掉（后台标签入口）。建议启动时遍历所有 leaf 的 document 注册一次。

**P1-8 无障碍（a11y）**

- `Sidebar.svelte:655-667`、`:716-738`：`div role="button"` 内部再放 `button`（twist / gacts / mx），嵌套交互元素；键盘 Tab 会停两次，屏幕阅读器语义混乱。
- 图标按钮只靠 `title`，没有 `aria-label`；搜索框没有 label；`styles.css:425,556` 对输入框 `outline:none`，键盘焦点不可见。
- 建议：行容器改 `role="group"` + `aria-expanded` / `aria-controls`；图标按钮补 `aria-label`；搜索框 `aria-label`；加 `:focus-visible` 样式。
- 这是 v1.1 的「可访问性收尾」，不是阻断项，但社区评审判断会看。

**P1-9 命令面板重复项**

- `commands.ts:81-92`：`open-sidebar` 与 `open-tab-manager` 两个命令，回调完全相同（都打开同一个侧栏）。2026-10-30 已向用户提过，待决定。

### 6.4 v2.0「自动」（2.0.0）——Smart Groups

**一句话**：让分组从「手工维护的桶」变成「按规则自动归位的视图」，但**规则是持久资产，成员是派生结果**，不引入第二套成员事实源。

**数据模型（schema v2）**

```ts
type GroupKind = 'manual' | 'smart';

type SmartRule =
  | { type: 'folder'; prefix: string; includeSubfolders: boolean }
  | { type: 'tag'; tag: string }
  | { type: 'property'; key: string; value?: string }
  | { type: 'glob'; pattern: string };

interface Group {
  id: string;
  name: string;
  color: ColorKey;
  kind: GroupKind;
  members: Member[];   // manual only; smart 恒为空
  rule?: SmartRule;    // smart only
}
```

**语义**

- 手动组：维持 R2（一文件一组）、现有全部入口与展开/收起。
- 智能组：成员由规则派生，**不写入 `members`**；一个文件可以同时出现在多个智能组（视图语义）；手动组仍互斥。
- 固定：固定标签从智能组成员中排除（派生过滤），不产生写操作，与 R6 一致。
- 展开：打开全部派生成员；**上限 100**（可设置），超过时弹确认「将打开 N 个标签，继续？」。
- 收起：关闭当前窗口内已打开的派生成员；固定/库外不动。
- 计数：`n/m`，m = 派生成员数；m 很大时显示 `n/120+`。
- 迁移：v1→v2 给所有现有组加 `kind: 'manual'`；`rule` 缺省；`schemaVersion: 2`；迁移链 + 单测 + `.bak` 保护。

**规则求值**

- 数据源：`app.vault.getFiles()` + `app.metadataCache.getFileCache(file)`；库外文件天然不在 vault 索引，自动排除。
- folder：路径前缀；`includeSubfolders` 控制是否包含子目录。
- tag：`metadataCache.getFileCache(file)?.tags`；支持 `#tag` 与嵌套 `#a/b`。
- property：frontmatter key/value；value 为空表示「有该 key」。
- glob：路径 glob（`*`/`**`/`?`），高级用户用。
- 求值时机：启动后 `metadataCache.on('resolved')`、vault create/rename/delete、规则变更；防抖 300ms；按规则缓存，只重算受影响的组。
- 性能：10k 文件、20 个智能组，目标单次求值 < 50ms；增量更新；面板只渲染打开标签 + 当前组。

**UI**

- 新建分组对话框加「Manual / Smart」切换；Smart 显示规则编辑器 + 实时预览「匹配 N 个文件」。
- 组头加「Smart」小徽标；菜单加「Edit rule…」「Convert to manual…」（把当前派生成员物化为 manual 成员）。
- 空智能组：「No files match this rule」+「Edit rule」。
- 搜索/展开/收起/计数沿用现有列表。

**一键起步**

- 「Create groups from folders」：扫描顶层文件夹，生成一组智能组（每个文件夹一个），让新用户 10 秒内看到价值。
- 「Create group from tag」：输入一个 tag，生成智能组。

**风险与缓解**

| 风险 | 缓解 |
|---|---|
| 规则太多、用户不懂 | 先只做 folder/tag/property 三种；glob 放高级 |
| 展开 500 个标签 | 上限 100 + 确认；显示匹配数 |
| 10k 文件性能 | 缓存 + 增量 + 防抖；基准测试 |
| 迁移损坏 | schema v2 单测 + `.bak` + 迁移前自动备份 |
| 智能组与手动组语义混淆 | 「Smart」徽标 + 文档 + 新建时解释；手动组仍互斥 |
| 规则与 pin 冲突 | 固定即从派生成员排除；不写数据 |

**DoD**

- schema v2 迁移测试（v1 数据 → v2，组/成员/颜色/顺序不变）。
- 规则求值单测（folder/tag/property/glob、嵌套 tag、大小写、库外排除）。
- 展开上限/确认、收起、计数、固定排除的 plan 测试。
- 10k 文件基准；面板 200 tabs 仍 < 16ms。
- 真实 Obsidian 验收：建智能组 → 打开文件 → 自动出现 → 展开/收起 → 重启 → 规则仍在。
- 2.0.0 Release + 迁移说明 + 回滚说明（保留 v1 `data.json.bak`）。
